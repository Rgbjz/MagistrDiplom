# Мок-подтверждение email при регистрации — дизайн (подпроект C)

**Дата:** 2026-06-01
**Статус:** утверждён (дизайн), ожидает ревью спецификации

## 1. Цель и контекст

Добавить подтверждение email при регистрации (без реальной отправки писем). Это **подпроект C** — последний в «Kwiga-like» апгрейде (после A — дизайн-система+кабинет, B — лендинги+покупки). Небольшой; реализуется одним планом.

## 2. Зафиксированные решения

| Вопрос | Решение |
|---|---|
| Доставка письма | **Мок:** после регистрации показываем экран «Подтвердите email» с кликабельной ссылкой (реальную почту не шлём) |
| Вход до подтверждения | **Запрещён:** логин неподтверждённого аккаунта отклоняется |
| Хранение токена | Поля на `User`: `emailVerified`, `verificationToken` |
| Существующие пользователи | Помечаются `emailVerified=true` (миграция + seed), чтобы текущие логины работали |
| Повторная отправка | Вне скоупа (YAGNI) |

## 3. Модель данных (Prisma)

В `model User` добавить:

```prisma
  emailVerified     Boolean  @default(false)
  verificationToken String?  @unique
```

Миграция: добавить столбцы; **установить `emailVerified=true` для всех уже существующих строк** (через SQL в миграции или последующий апдейт), иначе seed-аккаунты (teacher/student1/student2) не смогут войти. `seed.ts` создаёт пользователей с `emailVerified: true`.

## 4. Бэкенд

- **`POST /api/auth/register`** (меняется): создаёт пользователя с `emailVerified=false` и `verificationToken=<random hex (crypto)>`, профиль как сейчас. **Не логинит** (не создаёт Session, не возвращает токены, не ставит cookie). Возвращает `{ email, confirmToken }` (токен — для мок-ссылки). Дубликат email → `400` как сейчас.
- **`POST /api/auth/confirm` `{ token }`** (public, без guard): ищет пользователя по `verificationToken`; если найден → `emailVerified=true`, `verificationToken=null`, возвращает `{ ok: true }`; иначе `400 'Invalid or used confirmation link'`.
- **`POST /api/auth/login`** (меняется): после проверки пароля, если `!user.emailVerified` → `403 'Email not confirmed'`. (Проверка после пароля, чтобы не раскрывать существование аккаунта.) Auth.js Credentials при 403 вернёт null → неуспешный вход.

`AuthService`: `register` теперь возвращает `{ email, confirmToken }` вместо auth-ответа; добавить `confirm(token)`; в `login` добавить проверку `emailVerified`. `AuthController.register` больше не ставит refresh-cookie (возвращает body как есть).

## 5. Фронтенд

- **`RegisterForm`** (меняется): на успех `POST /auth/register` **не вызывает `signIn`**. Сохраняет `confirmToken` из ответа и показывает экран **«Подтвердите email»**: текст + кликабельная ссылка `/confirm?token=<confirmToken>` + подпись «в реальном продукте письмо ушло бы на вашу почту».
- **Страница `/confirm`** (public; читает `?token=`): на маунте вызывает `POST /api/auth/confirm { token }`; показывает «Email подтверждён ✓» + кнопку «Войти», либо ошибку «Ссылка недействительна или уже использована». Обёрнута в `<Suspense>` (используется `useSearchParams`, Next 15).
- **`LoginForm`**: при неуспехе текст подсказки «Проверьте email и пароль; убедитесь, что email подтверждён».
- **Middleware**: `/confirm` — публичный путь (наряду с `/login`,`/register`).

UI на дизайн-системе подпроекта A (UI-кит, токены).

## 6. Вне скоупа

- Реальная отправка email (SMTP/сервис).
- Повторная отправка ссылки, истечение срока токена.
- Восстановление/смена email.
- Спец-обработка сообщения «Email not confirmed» в Auth.js (логин просто не проходит; пользователю показывается общая подсказка).

## 7. Критерии готовности

- Регистрация создаёт неподтверждённый аккаунт и показывает экран со ссылкой подтверждения (без авто-входа).
- Переход по ссылке `/confirm?token=` подтверждает аккаунт; повторный/битый токен → ошибка.
- Вход неподтверждённого аккаунта не проходит; после подтверждения — проходит.
- Существующие seed-аккаунты (teacher/student1/student2) входят как раньше (они verified).
- Всё в теме A (светлая/тёмная).
